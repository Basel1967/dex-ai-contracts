# DEX AI Canonical Fact Contract v1.0.0

Status: Foundation Candidate — not published.

Stable ID: `urn:dex-ai:schema:fact:canonical-fact`

## Purpose and boundary

A Canonical Fact is the immutable, versioned statement currently supported about one canonical entity. It adjudicates typed Normalized Event evidence without inventing missing values. It is not a source event, risk judgment, score, recommendation, decision, trade instruction, Agent, Service, database, API, or execution engine.

## Dependencies and foundation scope

Event Envelope, Raw Event, and Normalized Event v1.0.0 are published, immutable dependencies. This slice permits only `MINT_INITIALIZED` for `SOLANA_MINT`, with value `{mint_address, initialized: true, synthetic}`. Absence of evidence never creates `initialized: false`. Evidence is accepted only from a successful or sufficient partial Normalized Event with complete lineage.

## Identity and versioning

`entity_id` is `urn:dex-ai:entity:solana:mint:<base58-address>`. `fact_id` is `urn:dex-ai:fact:<sha256>` deterministically derived from the contract namespace, entity ID, and fact type. It is stable across versions. Versions start at 1, are contiguous, immutable, and use `supersedes_version` for every version after 1. A semantic correction appends a version; history is never rewritten.

## Required payload

All fields are required. Only fields explicitly typed with `null` are nullable: `valid_to`, `supersedes_version`, `correction_reason`, and selected confidence/freshness members. The payload contains `fact_id`, `fact_version`, `entity_id`, `entity_type`, `fact_type`, `fact_value`, `fact_status`, `valid_from`, `valid_to`, `recorded_at`, `supersedes_version`, `correction_reason`, `evidence`, `resolution_status`, `confidence`, `freshness`, `lineage`, `canonicalization_profile`, `schema_ref`, `idempotency_key`, and `trace_id`.

## Evidence, correction, and conflict

Evidence records identify a Normalized Event, its payload hash, used JSON pointers, role (`SUPPORTS`, `CONTRADICTS`, or `CORRECTS`), event and observation times, entity references, and verified lineage. Evidence identity is unique by normalized event ID. The same ID with a different hash is an integrity violation. Newer arrival does not automatically win. An unresolved material contradiction requires `fact_status=CONFLICTED` and `resolution_status=UNRESOLVED`; arbitrary selection is forbidden. Corrections and retractions require a reason and a new version.

## Confidence, freshness, and validity

Confidence measures evidence support only; it is never risk, scoring, eligibility, safety, or a trade decision. Foundation defaults to `NOT_ASSESSED` with null score, method, and assessment time. Freshness is separate and defaults to `NOT_EVALUATED`; null expiry does not mean forever fresh. Validity uses `valid_from`/`valid_to`; null `valid_to` means unknown end, not permanent truth.

## Idempotency, ordering, and lineage

The idempotency key is derived from canonical JSON of entity, fact type, candidate value, deterministically sorted evidence, and canonicalization profile. Duplicate evidence has no effect. Event time provides semantic ordering; observation time records arrival. Late evidence is evaluated against its valid time and may confirm, conflict, or append a correction, but never overwrites history. Required lineage is Canonical Fact → Normalized Event → Raw Event → raw artifact/source, with field mappings and verified hashes.

## Prohibitions

This candidate changes no published dependency. It starts no Agent or Service and authorizes no later fact type, canonical store, risk, scoring, confidence engine, decision engine, watchlist, or auto-buy behavior.
